# Question 1:

Each line printed by pgtbltest represents a page table entry (PTE)
Each line includes:
+ va: virtual address of the page
+ pte: page table entry, which holds flags and the physical page number
+ pa: physical address of the page, which was calculated using PTE
+ perm: flags taken from PTE and printed independently, for better readability

Flags inside perm: V (validity), R (read allowed), W (write allowed), X (executable), U (user mode allowed), A (accessed) and D (dirty, which means it was written on).

Analysis of each page printed:
+ va 0x0 is where the machine code of pgtbltest are saved.
perm 0x5B means V, R, X, U, A are enabled.

+ va 0x1000 is where the data of pgtbltest are saved.
perm 0x17 means V, R, W, U are enabled.

+ va 0x2000 is the guard page, which stops the user from accessing beyond the user stack limit.
perm 0x7 means V, R, W are enabled. U = 0, so user mode cannot access this page.

+ va 0x3000 is the user stack for saving data when executing functions. 
perm 0xD7 means V, R, W, U, A, D are enabled.

+ Pages from va 0x4000 to 0x9000 has flag V = 0, which means they are unmapped.

+ Pages from va 0x3FFFFF6000 to 0x3FFFFFD000 has flag V = 0, which means they are unmapped.

+ va 0x3FFFFFE000 is the trapframe page, which stores the register values so that they can be restored when returning to user mode.
perm 0xC7 means V, R, W, A, D are enabled.

+ va 0x3FFFFFF000 is the trampoline page, which holds the code for switching between user and kernel mode.
perm 0x4B means V, R, X, A are enabled.


# Question 2:

vmprint() starts at the root page table of the process at 0x0000000087f25000. Then it recursively search using vmprint_walk() and print valid PTEs in a tree structure. Each .. represents a new level of the tree. In this example, PTEs with three .. are the leaf nodes, pointing to the physical pages that hold machine code or data of the process.

There are 6 leaf pages in the output:
 .. .. ..0x0000000000000000: pte 0x0000000021fc885b pa 0x0000000087f22000 RXU
Program machine code

 .. .. ..0x0000000000001000: pte 0x0000000021fc7c17 pa 0x0000000087f1f000 RWU
Program data

 .. .. ..0x0000000000002000: pte 0x0000000021fc7807 pa 0x0000000087f1e000 RW
Stack guard

 .. .. ..0x0000000000003000: pte 0x0000000021fc74d7 pa 0x0000000087f1d000 RWU
User stack

 .. .. ..0x0000003fffffe000: pte 0x0000000021fd08c7 pa 0x0000000087f42000 RW
Trapframe

 .. .. ..0x0000003ffffff000: pte 0x000000002000184b pa 0x0000000080006000 RX
Trampoline

R means read allowed, W means write allowed, X means executable and U means accessible from user mode. If any flag isn't included, that action is prohibited (For example: RXU means write not allowed)

The 6 leaf pages correspond to the 6 valid pages (V = 1) in the output of print_pgtbl() in Question 1. Their virtual addresses, PTEs and physical addresses all match.


# Question 3:

uptime() could be made faster by storing the number of clock ticks since boot in a page that user mode can only read. The kernel would update this value on each timer tick, and a user function could read it directly instead of trapping into the kernel. Since ticks are shared by all processes, one shared physical page would avoid updating a separate copy for every process. Reads and writes of the counter must be synchronized so user mode sees a consistent value.

sbrk(0) could also benefit from the per-process USYSCALL page. This call only returns the current process memory size without changing it. The kernel could store that size in the shared page and update it whenever the size changes, including after fork and exec. A user function could then read the size directly. Calls that grow or shrink memory would still need to enter the kernel.

This approach works for calls that only read information the kernel can safely expose. The user mapping must remain read-only so programs cannot change the kernel-maintained values.
